# Plan — Keystone 6.0 wrap-up (path to publishing 6.0.0)

Spec `2026-11-21-context-framework` is approved and the master plan
(`2026-11-21-context-framework`) is approved. This plan is the **remaining
work list**: what is already landed, what is missing, and the order to
finish so 6.0.0 can be tagged and published. Every workstream carries its
own acceptance criteria; the release gate is the spec's seven acceptance
criteria plus a green `keystone verify` on this repo's own tree.

## Workstreams

Order is fixed for W1–W2 before W5 (surfaces and drift land before the
self-migration exercises them); W3–W4 may interleave; W5–W7 land last.
Gate after each workstream: `go test ./...` green **and** `keystone verify`
green on this repo.

### W1 — Flywheels on every surface (learning, improvement, pruning, auditing)

Decision 15 (availability over adoption): every capability is invocable by
users, scripts, rules, skills, and hosts through CLI **and** MCP — never
only a planted skill.

1. CLI verbs: `keystone synthesize` (promote inbox candidates up the
   corpus → reference → rule ladder), `keystone audit` (dual-flywheel:
   learning capture + pruning of dead primitives), `keystone mode
   [paired|solo|autopilot]`. `learn` already exists.
2. MCP tools: `keystone_learn`, `keystone_synthesize`, `keystone_audit`,
   `keystone_mode` — same behavior, descriptors + paths, shelling to the
   same framework functions as the CLI.
3. Skills stay as thin wrappers for teams that plant them.

**Acceptance criteria:** from a scratch `keystone init` with no lifecycle
skills planted, `keystone learn x --body …` → `keystone_learn` visible in
the MCP tool list → `keystone synthesize` promotes a fixture candidate to
the proposed layer → `keystone audit` reports inbox + dead-primitive
findings → `keystone mode` round-trips the mode state; each verb has a
`--json` form for scripts; the same flow completes through MCP tools
alone.

### W2 — Context drift (spec pillar 2; plan phase 5)

Approve the draft mini-plan `2026-11-21-context-drift.md`, then implement:

1. `keystone drift [files…|--diff] [--json]` — dead relative links, `paths:`
   globs matching zero files, `verified:` older than `drift.days`
   (default 90). Warnings only; keystone names stale context, never judges
   the diff (decisions 12/16).
2. `verified:` surfaced in `show`, INDEX, and the dashboard.
3. `keystone verify` reports stale-but-in-scope primitives as warnings.
4. MCP `keystone_drift_report` (descriptors only) + dashboard drift pane.

**Acceptance criteria:** the mini-plan's fixture reports exactly three
named warnings; a clean tree reports zero; `verify` surfaces staleness;
`show` prints `verified:`; MCP and the pane read the same data.

### W3 — Lazy-load hardening (plan phase 6)

1. AGENTS.md managed block shrinks to: what the charter is (the codified
   context in this repository), how to query it (CLI one-liners + MCP tool
   names), the index pointer, the per-host line. No inlined primitive
   bodies.
2. Default `always_loaded` budget cap; `keystone verify` fails overages
   naming file + overage; `keystone budget` reports the tier.

**Acceptance criteria:** fresh-init AGENTS.md block contains no primitive
body text; this repo's always-loaded tier ≤ cap after W5 conversion;
`verify` green.

### W4 — Projection demotion, minimal and clean (plan phase 7)

1. `keystone init` writes an empty `adapters` list by default; host
   projection requires explicit opt-in (`keystone target add …`) and says
   so in its output.
2. `doctor` reports configured adapters as opt-in state.
3. `hosts.md` header gains the compat notice; README/docs re-order query
   layer first, projection under "compat".
4. Minimality pass over projection: collapse redundant strategies, drop
   dead options — same behavior, less machinery, green after each step.

**Acceptance criteria:** fresh `keystone init` in a temp dir writes
nothing outside `.agents/`, `.keystone/`, `keystone.json`, and the
AGENTS.md block (filesystem diff); opt-in `keystone project` for
claude-code still passes with a green lockfile.

### W5 — Dogfood this repo (plan phase 8.1)

1. `keystone migrate up` (applies `v6_0`): `agent` kind renames, alias
   rewrites, category fields stripped from state files.
2. `keystone index` — INDEX/INDEX.lite regenerate with kind/id/description
   only; adopted corpus entries carry `provenance: repo`.
3. Add `charter.roots` to this repo's `keystone.json` adopting
   `GLOSSARY.md` and `docs/**/*.md` in place — unmoved, unedited.
4. `keystone project` — regenerate the AGENTS.md managed block from the
   W3 template.
5. **Relocate constraints to better locations** with the ladder: audit
   this repo's own rules and move each to the kind that fits — a rule that
   is really an executable check becomes a `hook` (e.g. verification /
   commit-message style rules), pure rationale demotes to `reference`,
   standalone facts to `corpus`. Use `keystone charter move|promote|demote`
   so citations and the index rewrite themselves.
6. This repo's phased lifecycle stays as the worked example behind the
   opt-in `--starter workflow` pack — not planted by default anywhere.

**Acceptance criteria:** `keystone verify` green on this tree (zero
pending migrations, zero projection drift); `keystone search glossary`
finds `GLOSSARY.md` in place; `charter query internal/framework/` returns
the path-scoped rules in descriptor form; every relocated primitive shows
updated citations in `explain`.

### W6 — Terminology and docs sweep (spec AC 4)

1. README leads with the context framing + the query front door

3. CONTRIBUTING, `docs/kinds/README.md`, `docs/hosts.md`, install/init
   messages swept.
4. `rg -i 'constraint|capability'` over the tree returns only CHANGELOG

**Acceptance criteria:** the `rg` sweep is clean; README, GLOSSARY, MCP
`instructions`, and the AGENTS.md template all state the same charter
definition; `keystone migrate` + `lint --fix` bring a 5.x fixture tree to
green 6.0.
