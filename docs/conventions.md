# Keystone conventions

<!-- voice-register: informational -->
<!-- voice-english: ste -->

This page is the convention table for a 5.0 charter. Use it to find the folder and generator for each kind. It also covers the rules that cross every kind: override, rule tiers, pacing modes, and links. For per-kind fields, open the kind pages in [`kinds/`](kinds/README.md). `keystone new` writes conformant files, and `keystone lint` and `keystone doctor` check the ones you already have.

`<repo-root>` is the project root, the folder that holds `keystone.json`.

## Directory layout

A 5.0 install uses two folders: `.agents/` holds what you author, and `.keystone/` holds what keystone writes and keeps.

```
<repo-root>/
├── keystone.json                    # project config (you edit it)
├── AGENTS.md                        # keystone writes a managed block
├── CLAUDE.md                        # keystone writes a managed block (@AGENTS.md)
├── .agents/                         # the charter: one folder per kind
│   ├── rules/<topic>/<name>.md
│   ├── references/<topic>/<name>.md
│   ├── hooks/<id>.md
│   ├── permissions/<id>.md
│   ├── evals/<id>/EVAL.md
│   ├── skills/<id>/SKILL.md
│   ├── commands/<id>.md
│   ├── agents/<id>.md               # kind: subagent
│   ├── tools/<id>.md
│   └── documents/<id>.md
├── .keystone/                       # keystone's state
│   ├── INDEX.json, INDEX.lite.json  # generated by keystone index
│   ├── lockfile.json                # installed policies and owned host files
│   ├── policies/<policy>/           # vendored policy trees
│   ├── hosts/<host>/                # per-host lifecycle docs
│   ├── learning/                    # the learning flywheel
│   ├── archive/                     # the pruning flywheel
│   └── work/, state/, sources/
└── .claude/, .cursor/, .github/, …  # generated by keystone project
```

Four invariants hold:

- **One source per primitive.** The source lives under `.agents/`, and `keystone project` writes the host files from it. So edit the source, never the projection.
- **The lockfile records ownership.** Keystone records each host file it writes, so `keystone project` never replaces a file it didn't write. To replace one, pass `--overwrite`.
- **The index is the shared view.** `keystone index` writes `.keystone/INDEX.json`, and the CLI, the MCP server, and the dashboard read it. For its shape, see [`kinds/README.md`](kinds/README.md).
- **`keystone.json` stays at the repo root**, next to the other project config.

## Kinds

The kind comes from the first folder under `.agents/`, so you can leave `kind:` out.

| Kind | Category | Folder | Generator |
|---|---|---|---|
| [`rule`](kinds/rule.md) | constraint | `rules/<topic>/<name>.md` | `keystone new rule <topic>/<name>` |
| [`reference`](kinds/reference.md) | constraint | `references/<topic>/<name>.md` | `keystone new reference <topic>/<name>` |
| [`hook`](kinds/hook.md) | constraint | `hooks/<id>.md` | `keystone new hook <id>` |
| [`permission`](kinds/permission.md) | constraint | `permissions/<id>.md` | `keystone new permission <id>` |
| [`eval`](kinds/eval.md) | constraint | `evals/<id>/EVAL.md` | `keystone new eval <id>` |
| [`skill`](kinds/skill.md) | capability | `skills/<id>/SKILL.md` | `keystone new skill <id>` |
| [`command`](kinds/command.md) | capability | `commands/<id>.md` | `keystone new command <id>` |
| [`subagent`](kinds/subagent.md) | capability | `agents/<id>.md` | `keystone new subagent <id>` |
| [`tool`](kinds/tool.md) | capability | `tools/<id>.md` | `keystone new tool <id>` |
| [`document`](kinds/document.md) | capability | `documents/<id>.md` | `keystone new document <id>` |

Two frontmatter keys cross kinds:

- **`paths:`** scopes a rule to the files it governs. A rule without `paths:` applies everywhere.
- **`event:`** names what fires a hook, a tool, or a subagent. A host event (`PreToolUse`, `Stop`) bridges into the host. Any other name is a signal that keystone fires.

Keystone still reads the 4.x keys `globs:` and `on:`, and the 4.x kind names. `keystone lint` warns on each one, and `keystone lint --fix` rewrites them. [`compatibility.md`](compatibility.md) lists what stays readable.

## Projection

`keystone project` delivers each primitive to every host in `keystone.json` `adapters`, and Claude Code is always on. To see the strategy per host and kind, open [`hosts.md`](hosts.md).

A primitive projects under its own id, in kebab case. For example, the subagent `reviewer` becomes `.claude/agents/reviewer.md`, and the command `release` becomes `/release`. 4.x added a `keystone-` prefix to every projected name, but 5.0 drops it. The exception is an id that already starts with `keystone`, such as `keystone-verify`, which keeps its prefix.

## Override

Your files in `.agents/` override installed policies in `.keystone/policies/`. Among policies, a policy nested deeper in `keystone.json` refines the outer policy. But a policy's `strict:` item is absolute, so nothing can override it.

The cascade code still keys `strict:` and `required:` on the 4.x folder names: `guides`, `playbooks`, `actions`, and `sensors`. Whether it matches a 5.0 folder is unverified.

## Hook depth limit

Only the project and top-level policies may ship checks. Here, a top-level policy is one with no policy above it in `keystone.json`. If a nested policy ships checks or claims them in `strict:`, `keystone verify` fails with a `DepthViolation`.

The check reads the 4.x names: the `sensors/` folder and `strict.sensors`. Whether it also catches a nested policy's `hooks/` folder is unverified.

## Rule tiers

A rule's body groups its directives in three tiers. Only the last tier is required.

| Tier | When |
|---|---|
| `## IRON LAW(S)` | Non-negotiable. A violation causes real damage. Rare by design. |
| `## GOLDEN RULE` | Stronger than a regular rule. A deviation needs stated reasons. |
| `## RULES` | Regular rules. The default tier; most directives go here. |

An iron law wins over any conflicting instruction. A golden rule, in contrast, yields to explicit reasoning, and a regular rule yields when a stronger rule applies. For the rest of the body, see [`kinds/rule.md`](kinds/rule.md).

## Pacing modes

A mode sets how often the agent stops to ask. It is separate from the lifecycle phases.

| Mode | Behavior |
|---|---|
| `paired` | The agent asks for feedback at phase boundaries and decision points. The default. |
| `solo` | The agent works alone, but stops on ambiguity, rule conflicts, and failures it can't explain. |
| `autopilot` | The agent works through the lifecycle without prompts. It stops only when blocked. |

The `**Active mode:**` line in `.agents/rules/process/modes.md` is the source of truth. To switch, run the `mode` command with the mode name. Then check `.keystone/hosts/<host>/lifecycle.md`, which says how your host runs it. If your host has no idea of autonomy levels, you can ignore modes.

## Agent failure modes

Process rules under `.agents/rules/process/` guard against failures that recur across agents. Each rule has no `paths:`, so it applies everywhere.

| Rule | The failure it guards against |
|---|---|
| `dangerous-actions.md` | Operations that are hard to reverse: destructive git, force-push, dropped tables. |
| `escalation.md` | Not knowing when to stop and ask, and what to tell the user. |
| `grounding.md` | Invoking a function, flag, or file that doesn't exist. |
| `pushback.md` | Complying in silence when the user is wrong. |
| `sensitive-files.md` | Reading or writing secrets such as `.env*` and credentials. |
| `subagent-trust.md` | Accepting a subagent's report without checking it. |
| `self-validation.md` | Counting the agent's own claim as evidence. |

They are ordinary rules, not a kind of their own, and `.agents/rules/process/README.md` lists them.

## Learning and pruning

Two flywheels keep your charter current. Neither is a kind: both are folders that commands write to.

- **Learning.** The `learn` command writes a candidate, with its evidence, to `.keystone/learning/inbox/<timestamp>-<slug>.md`. The `synthesize` command promotes it to a rule or a reference, or rejects it with a reason.
- **Pruning.** The `audit` command finds stale rules and references. It moves each one to `.keystone/archive/` with a one-line reason.

For the full contract, see [`internals/flywheel-sink.md`](internals/flywheel-sink.md).

## State ledgers

State ledgers record what is true about this project now. You keep them in `.agents/references/state/`, and only the project ships them. Keystone recognizes these files: `CODEBASE_STATE.md`, `INSTALL_PROFILE.md`, `code-debt.md`, `charter-debt.md`, `quality-radar.md`, `risk-fingerprints.md`, and `traffic-topology.md`. A writer rewrites only the sections it names and keeps the rest. For the full contract, see [`internals/state-ledger.md`](internals/state-ledger.md).

## Path conventions

A link in a charter file is plain Markdown: it resolves from the folder of
the file that holds it, so it works in an editor, on GitHub, and for an
agent that opens the file.

```markdown
<!-- inside .agents/rules/process/spec.md -->
For reasoning, see [`references/process/spec.md`](../../references/process/spec.md).
See [`keystone.json`](../../../keystone.json) for the policy pins.
```

`keystone project` rewrites each relative link in a shim (a translated
host copy, such as `.cursor/rules/spec.mdc`) so it resolves from the
copy's folder. `keystone doctor --paths-only` fails on any relative link
under `.agents/` that names no file.

A skill keystone links or copies into a host folder keeps its links as
written, so keep a skill's links inside its own folder where you can.

## Authoring

Each kind has a one-line generator. It writes a skeleton with the right frontmatter, path, and headings, and then you fill in the body.

```
keystone new <kind> <id>     # rule | reference | hook | permission | eval
                             # skill | command | subagent | tool | document
keystone new adapter <host>
keystone new policy <name>   # a new policy repo
```

`keystone new rule` also writes the paired reference. The 4.x kind names (`guide`, `corpus`, `sensor`, `posture`, `agent`, `playbook`, `pattern`) exit with an error that names the 5.0 kind.

The skeletons live in `internal/framework/scaffold/templates/`, embedded in the binary. A template change affects new files only, so the doctor reports template drift in files you already have.

After you add, move, or delete a primitive, run `keystone index && keystone project`.

## Internals

- **Budget.** `keystone.json` `budgets` caps what each host loads. Keys are `always_loaded` or a kind name. `keystone budget` and `keystone verify` fail on an exceeded cap. See [`internals/budget.md`](internals/budget.md).
- **Patch.** `keystone patch` applies framework patches to config files. See [`internals/patch.md`](internals/patch.md).
- **Host docs.** `.keystone/hosts/<host>/` holds each host's lifecycle notes. See [`internals/host-docs.md`](internals/host-docs.md).
