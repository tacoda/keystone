Guide · Keystone v5.0.2

Get started with Keystone.

Keystone keeps the standards for your coding agents in one folder, .agents/, and delivers them to every agent you use. This guide takes you from install to a charter with one rule and one hook. Work through it in order, because each step uses the last one.

What Keystone does

You write your standards once, as plain Markdown files in .agents/. Then keystone project writes them into each host's own format. The hosts are Claude Code, Cursor, Copilot, Codex, opencode, Continue, Cline, Goose, Pi, and Aider. Where a host can't enforce something, Keystone tells you, and it tells the agent too.

That set of standards is a charter. Keystone keeps its own state, such as the index and the lockfile, in .keystone/. You edit .agents/, and you never edit .keystone/ by hand.

What you'll have at the end

  • Keystone installed, and a charter in your repo.
  • One rule that applies only to the files it names, with its reasoning one hop away.
  • One hook that blocks the agent when a check fails.
  • Both delivered to your host by keystone project.

Harness vs. charter

A harness runs the model: the coding agent, the orchestrator, the runner. A charter is the set of standards that constrains that harness. Keystone manages the charter, so it isn't a harness. Swap agents, and the charter stays.

The three surfaces
authoring

CLI

The keystone binary scaffolds, indexes, projects, and verifies the charter.

dispatch

MCP server

Serves the same charter to your agent as MCP tools, and your host starts it.

observe

Dashboard

A local view at http://localhost:4773 for coverage, the budget, signals, and evals.

Remember An agent can read the charter with none of these tools, because it's plain files. Hooks are the one exception: each host bridge calls the keystone binary on your PATH.
Coming from 4.x? Run keystone migrate up, then install the 5.0 binary before your hooks run again. The 4.x names still parse, and keystone lint --fix rewrites them. See the reference for the map from each old name to its new one.

Guide · Step 2

Install Keystone

Install the binary, run keystone init in your repo, and connect your agent to the MCP server. That's three commands.

1. Install the binary

Install it from the Homebrew tap, or download a release binary from GitHub:

$ brew install tacoda/tap/keystone
~/my-project
$ keystone init --agent claude-code
▸ installing charter to .agents
▸ installing keystone state to .keystone
wrote: .keystone/INDEX.json (81 primitive(s))
wrote: AGENTS.md
wrote: CLAUDE.md
✓ charter installed for claude-code.
▶ Next: run the /keystone:bootstrap skill in claude-code.
$ keystone mcp install --agent claude-code
✓ wrote .mcp.json
$ claude
> /keystone-bootstrap
✶ Thinking… (3s · esc to interrupt)

2. Run keystone init

Run keystone init from the root of your repo. Pass --agent to name your host. Without the flag, init asks you to pick one in a terminal: 

$ keystone init                     # asks you to pick your agent
$ keystone init --agent claude-code  # no questions

Pass one of these host names to --agent: 

claude-code  codex  cursor  github-copilot  opencode
continue  cline  goose  pi  aider  generic

Init writes .agents/, .keystone/, keystone.json, and AGENTS.md, and then it projects your host. It skips every file that already exists. If you want it to replace Keystone's own files, pass --overwrite.

Init ends with a next step: run the keystone-bootstrap skill in your agent. That skill reads your codebase, detects the stack, and fills .agents/references/state/CODEBASE_STATE.md.

3. Connect your agent to the MCP server

This command writes the host's MCP config, and the host starts the server on its next session: 

$ keystone mcp install --agent claude-code   # writes .mcp.json
# cursor → .cursor/mcp.json · codex → .codex/mcp.json · opencode → opencode.json
Optional Run keystone web serve to open the local dashboard at http://localhost:4773. You don't need it to follow this guide.

Guide · Step 3

Your first charter

Look at what init gave you: two folders, ten kinds of primitive, and one entry file that every host reads.

Two folders

.agents/ holds the sources you edit. .keystone/ holds Keystone's state. Here's the shape after init:

.agents/
├─ rules/directives the agent follows
├─ references/the reasoning behind each rule
├─ hooks/checks that run on an event
├─ skills/Agent Skills, including the keystone-* lifecycle skills
└─ agents/ commands/ evals/subagents, commands, and evals
.keystone/
├─ INDEX.json INDEX.lite.jsonthe descriptor index, read first
├─ lockfile.jsonevery file Keystone wrote
└─ learning/the learning inbox

keystone.json stays at the repo root. It lists your hosts under adapters and your vendored policies under policies: 

// keystone.json
{
  "version": "2",
  "policies": [],
  "adapters": [
    "claude-code"
  ]
}

Two categories, ten kinds

Every file in .agents/ is a primitive of one of ten kinds. Constraints limit, gate, or check what the agent does. Capabilities add things the agent can do. Keystone reads the kind from the folder, so you can leave kind: out.

This guide covers the two kinds you'll write first: a rule and a hook. Read the reference for the other eight.

AGENTS.md, the entry file

AGENTS.md is the file every host reads first. Keystone writes a managed block into it, between <!-- keystone:start --> and <!-- keystone:end -->. The block holds the orientation, the iron laws, the rules that apply everywhere, and one line per host. Keystone rewrites only that block, so your own text around it stays.

CLAUDE.md gets a block that imports AGENTS.md: 

<!-- keystone:start -->
@AGENTS.md

Read [`AGENTS.md`](AGENTS.md) before anything else in this repo: it carries the iron laws and how the charter activates. The import above loads it.
<!-- keystone:end -->

Guide · Step 4

Your first rule

A rule is a directive the agent follows. Write one that applies only to your migration files, and put its reasoning in a paired reference.

Say your repo has a Rails backend, and you want migrations to stay small and reversible. Scaffold a rule with keystone new rule <topic>/<name>: 

$ keystone new rule rails/migrations
  wrote: .agents/rules/rails/migrations.md
  wrote: .agents/references/rails/migrations.md

The generator writes two files: the rule and its paired reference. The rule's corpus: field already points to the reference. Open the rule, and replace the placeholders: 

# .agents/rules/rails/migrations.md
---
kind: rule
id: rails/migrations
description: Migrations are small and reversible.
paths:
  - "db/migrate/**"
corpus:
  - rails/migrations
---

# Migrations

## Rules

- Keep each migration reversible and scoped to one change.
- Never mix a schema change and a data backfill in one migration.

For reasoning, see [`references/rails/migrations.md`](../../references/rails/migrations.md).

Scope it with paths:

paths: is a list of globs. The rule applies when a file the agent touches matches one of them, and ** matches any number of folders. A rule without paths: applies everywhere.

paths: only narrows where a rule applies. It can't make a rule apply in more places. If no pattern matches a real file, the rule never applies, so check each pattern against your tree.

Put the reasoning in the reference

The rule says what to do, and the reference says why. The agent opens a reference only when the rule's body isn't enough, so the rule can stay short. Edit the reference that the generator wrote: 

# .agents/references/rails/migrations.md
---
kind: reference
id: rails/migrations
description: Why migrations stay small and reversible.
---

# Why migrations stay small

An irreversible migration can't be rolled back cleanly in an
incident. A migration that mixes a schema change and a backfill
locks tables for the duration of the backfill.
Tip Host shims copy only these sections from a rule body: Iron law, Iron laws, Golden rule, Golden rules, Rules, and Anti-patterns. Put your directives under one of them.

Guide · Step 5

Project to your hosts

keystone project delivers .agents/ to every host in keystone.json. Run it after you add, move, or delete a primitive. 

$ keystone index && keystone project
✓ keystone index — wrote .keystone/INDEX.json (83 primitive(s) across 5 kind(s))
✓ keystone index — wrote .keystone/INDEX.lite.json (lite descriptor)
  wrote: .claude/rules/rails-migrations.md
✓ keystone project — 1 written, 46 unchanged, 0 pruned

keystone index rebuilds the descriptor index. keystone project then writes each host's files. On Claude Code, your rule becomes a shim in .claude/rules/. The shim keeps your paths: and copies the ## Rules section: 

# .claude/rules/rails-migrations.md
---
description: Migrations are small and reversible.
paths:
  - "db/migrate/**"
source: .agents/rules/rails/migrations.md
generated_by: keystone-project
---

# Migrations

Full rule: `.agents/rules/rails/migrations.md` (read on demand).

## Rules

- Keep each migration reversible and scoped to one change.
- Never mix a schema change and a data backfill in one migration.

How each host gets a primitive

Keystone picks the cheapest method that each host supports:

  • Native. The host already reads the path. Codex and opencode read .agents/skills/.
  • Link. The host reads the same format at another path. Claude Code gets a symlink per skill in .claude/skills/.
  • Shim. The host needs a different format. Cursor gets .mdc rules, and Copilot gets .instructions.md files.
  • Index. The host has no slot for the kind. AGENTS.md lists it, and the agent opens it from .agents/ when it applies.

A rule without paths: goes into the AGENTS.md block as one line, with its path and description. The agent opens the body when it applies.

Add a host

To add a host, add its name to adapters in keystone.json. Then run keystone project again: 

// keystone.json
{
  "version": "2",
  "policies": [],
  "adapters": [
    "claude-code",
    "cursor"
  ]
}

For an agent that Keystone has no profile for, run keystone new adapter <name>. It writes .agents/hosts/<name>.json, which sets one method per kind.

Keystone records every file it writes in .keystone/lockfile.json. It never replaces a file that it didn't write.

Tip keystone watch re-indexes and re-projects on every save under .agents/. Keep it open in a side terminal while you write.

Guide · Step 6

Your first hook

A rule is text, so the agent can ignore it. A hook is a check, and on a host with a hook bridge, a failing check blocks the agent. Write one that runs your tests when the agent finishes its turn. 

$ keystone new hook tests
  wrote: .agents/hooks/tests.md

The generator writes mode: computational, event: Stop, and a placeholder run: "true". Replace the placeholder, because it always passes: 

# .agents/hooks/tests.md
---
kind: hook
id: tests
description: Block the turn when the test suite fails.
mode: computational
event: Stop
run: bin/rails test
---

# tests

A non-zero exit means a test failed. Read the failure and fix it before you claim done.

event: and run:

event: names when the hook fires. run: is the shell command. If the command exits non-zero, the hook blocks. Without event:, the hook never fires.

Host events and signals

An event: value is one of two things:

  • A host event is one the host fires, such as Stop. The full set is PreToolUse, PostToolUse, UserPromptSubmit, Notification, Stop, SubagentStop, PreCompact, SessionStart, and SessionEnd.
  • A signal is any other name. Keystone fires pre-verify and post-verify around keystone verify, and you fire any signal with keystone signal fire <name>. A signal never reaches the host.

keystone signal list shows the built-in signals and the ones that keystone.json declares under signals.

Bridges fail closed

Run keystone index && keystone project again. Keystone writes one bridge per host event. On Claude Code, the bridge goes into .claude/settings.json, next to your own hooks: 

// .claude/settings.json (hooks.Stop)
"command": "keystone hook fire Stop --host claude-code || exit 2"

When the host fires the event, the bridge runs every hook with that event: in parallel. If any command exits non-zero, the bridge exits 2, and the host treats that as a block. A missing binary or a bad flag also exits 2, so the bridge fails closed.

Fire the event yourself to see a block. In this example repo, bin/rails doesn't exist yet, so the hook fails: 

$ keystone hook fire Stop --host claude-code
✗ hook tests: exit status 127
bash: bin/rails: No such file or directory
keystone: hook fire Stop: 1 hook(s) failed
$ echo $?
2

On a host event, a command that runs past 50 seconds also counts as a failure. A hook has no matcher of its own, so a PreToolUse hook runs before every tool call.

Where hooks block Claude Code, Cursor, Copilot, Codex, and opencode get a bridge. I've run the block on Claude Code. For the other four, it's what each host's hook docs specify. Every other host gets no bridge: keystone project reports the gap, and AGENTS.md tells the agent to run the checks itself.

A hook can also be inferential: the body is a review prompt, and returns: sets the verdict the agent must fill. The reference covers that mode and the per-host details.

Guide · Step 7

Bring an existing setup

Already have a CLAUDE.md, Cursor rules, or Copilot instructions? keystone allocate tells you where each item belongs in .agents/.

Allocate reads .claude/, .cursor/rules, .cursorrules, Copilot instructions, .clinerules, .windsurfrules, .continue/, and .opencode/. For each item, it reports the kind and the .agents/ path. Here it is on a repo with one Cursor rule: 

$ keystone allocate
keystone allocate — 1 item(s) move into .agents/, 0 stay

  .cursor/rules/go.mdc → rule .agents/rules/go.md
      globs → paths

Run `keystone allocate --apply` to write these into .agents/ (originals stay in place).

Allocate also splits CLAUDE.md, AGENTS.md, GEMINI.md, and .goosehints into sections. It proposes moving each section that doesn't need to load every session. A section that names file patterns becomes a path-scoped rule, and a numbered procedure becomes a command. Long reasoning becomes a reference, and iron laws stay where they are.

  • keystone allocate writes nothing.
  • keystone allocate --apply writes new files under .agents/ and changes no original.
  • keystone allocate --overwrite hands the originals to Keystone, so the next projection replaces them.
Tip Run the report first, and read it. Use --overwrite only when you're ready for Keystone to own those files.

Guide · Step 8

Check the context budget

Each host loads part of the charter at the start of every session. keystone budget shows how much, per host. 

$ keystone budget
Context budget (word-count estimate; real tokenizers count about 1.35× more)

Always loaded, per host:
  claude-code       1506
         788  AGENTS.md (root)
  …

On demand (opened when they apply): 21031
  rule             10371
  reference         2810
  skill             6278
  subagent          1572
  …

The always loaded tier is what the host reads at the start of every session. That tier holds root files, rules without paths:, and the name and description of every skill, command, and subagent. The on demand tier is every body the agent opens when it applies.

The numbers are a word-count estimate. Real tokenizers count about 1.35 times more, and the caps use the same estimate. Set caps in keystone.json: 

// keystone.json
"budgets": {
  "always_loaded": { "max_tokens": 4000 },
  "reference":     { "max_tokens_per_load": 3000 }
}

When a cap is exceeded, keystone budget exits non-zero. keystone verify runs the same check, and it names the file and the overage. Pass --json to read the result in CI.
