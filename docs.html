The Keystone reference.

Keystone is the agent charter framework. You write the standards your coding agents follow once, in .agents/. Keystone delivers them to ten hosts and tells you where a host can't enforce one. This page is the full reference for v5.0.1. For a first look, read the home page. For a task walkthrough, read the guide.

Context budget

Concepts

Charter vs. harness

The distinction that names the tool: a harness runs the model, and a charter is the standards you write to constrain it. Keystone manages the charter.

Charter

What you author

Rules and their references, hooks, permissions, evals, skills, commands, subagents, tools, and policy. Your CLAUDE.md and AGENTS.md are charter too. It lives in .agents/.

Harness

What you run

The coding agent (Claude Code, Cursor, Codex, …), agent frameworks, and the orchestrator, loop, or runner that fires your hooks.

The test

Authorship, not executability. A pre-commit hook runs, and it's still charter, because you wrote it to state a standard. The runner that fires that hook is the harness.

Author the spec: charter. Be the engine: harness.

The orchestrator splits the same way. It runs, so it's harness. The process it enforces is authored, so that's charter.

The kind comes from the folder

Keystone reads the kind from the first folder under .agents/, so you can leave kind: out. Skills and evals are folders: the indexer reads SKILL.md and EVAL.md. In the other folders, it reads every .md file except README.md. keystone lint reports any other kind as an error.

Shared frontmatter
---
id: process/verification          # required; the join key in the index
description: The phase where claims are paired with evidence.  # required; one line
tags: [process]                   # optional, kebab-case
corpus: [process/verification]    # optional: references this primitive cites
supersedes: [process/old-verify]  # optional: ids this primitive replaces
---

Write description so the agent can decide from the index alone whether to open the body. A skill sets name: instead of id:.

The index

keystone index walks .agents/ and writes two files under .keystone/. The write is atomic, so an agent never reads a partial file. The index holds descriptors only, never bodies.

INDEX.json holds each full descriptor with its path and provenance, plus the maps by_kind, by_category, and by_path. INDEX.lite.json holds only category, kind, id, and description. Read the lite file first.

After you add, move, or delete a primitive, run keystone index && keystone project. Or run keystone watch in a side terminal.

The ten hosts

Claude Code, Cursor, GitHub Copilot, Continue, opencode, Codex, Cline, Goose, Pi, and Aider. Every host but two reads AGENTS.md natively. Claude Code gets a CLAUDE.md that imports it, and Aider gets read: entries in .aider.conf.yml. Each kind page lists what its hosts get. The full matrix, with the host docs behind each cell, is docs/hosts.md ↗.

What keystone owns

The AGENTS.md block. Keystone writes only between <!-- keystone:start --> and <!-- keystone:end -->. The block holds the orientation, the iron laws, the pathless rules, the tools, and one line per host. Your text around it stays. CLAUDE.md gets a block that imports AGENTS.md.

The lockfile. Keystone records every file it writes in .keystone/lockfile.json. keystone project replaces only those files. A file it didn't write stops the run, unless you pass --overwrite.

Names. A primitive projects under its own id in kebab case. The subagent reviewer becomes .claude/agents/reviewer.md, and the command release becomes /release.

Edit the source, never the projection. The next keystone project overwrites a projected file.

Custom hosts
{
  "name": "zed",
  "kinds": {
    "skill":    { "strategy": "link", "dir": ".zed/skills" },
    "rule":     { "strategy": "copy", "dir": ".zed/rules" },
    "command":  { "strategy": "index" },
    "subagent": { "strategy": "native" }
  }
}

For an agent without a built-in profile, run keystone new adapter <name>. It writes .agents/hosts/<name>.json, with one strategy per kind: native, link, copy, or index. A kind you leave out is indexed. Then run keystone target add <name>.

A custom host gets no format conversion, no hook bridge, and no permission translation, so keystone reports its hooks and permissions as gaps. dir must stay inside the repo and outside .agents/ and .keystone/.

How a bridge blocks

Each bridge runs keystone hook fire <event> --host <host>, as Events shows. If any check exits non-zero, the bridge exits 2, which each host's docs define as a block. A missing binary, a bad flag, or a check past 50 seconds also exits 2, so the bridge fails closed.

I've run the block on Claude Code. For Cursor, Copilot, Codex, and opencode, the behavior is what each host's hook docs specify. A pass prints what the host parses (JSON for Cursor and Codex) and keeps keystone's own lines on stderr.

If you enable both Claude Code and Copilot, a hook can run twice, because Copilot also reads .claude/settings.json. keystone project warns about it.

How permissions translate

Write each rule once, in Claude Code syntax: Tool or Tool(specifier). For Bash, a specifier that ends in :* is a prefix match. A translation may make a deny or ask stricter. It never makes an allow broader than the rule you wrote, so keystone reports a rule instead of widening it.

Cursor has no ask, so keystone reports every ask rule. Codex takes only Bash rules, and keystone reports an exact-command allow. On both, keystone reports a * inside a Bash specifier.

Claude Code and Cursor share the file with your own settings. Keystone records each entry it adds and removes only those entries. An entry you had before keystone added it stays.

Concepts

Resolution order: rules, references, ask

The MCP server's instructions and the runtime-resolution rule give the agent the same order. The agent moves to the next stage only when the current stage isn't enough to act.

  1. Rules.

    Find the rules for the touched files and the current phase. The project wins by default, policies refine it, and a strict item is absolute.

  2. References.

    When a rule's body isn't enough, open the references its corpus: field links. Nothing loads a reference until the agent asks for it.

  3. Contradictions: ask.

    When a rule and its reference disagree, ask the user. Keystone doesn't check that they agree.

A tool isn't a stage. To reach an outside system, the agent calls a tool. Tools sit beside this order, not inside it.

Three stages, each one only when the last isn't enough

by paths and phase] R -->|enough to act| DONE[Act] R -->|body too short| C[2 · References
follow corpus:] C -->|no conflict| DONE C -->|rule vs reference| A[3 · Ask
the user decides] A --> DONE
ConceptsThe cascade →
Concepts

The cascade

How keystone picks one file when your project and a vendored policy both define an item. Exactly one file wins, and keystone never merges the two.

  1. The project wins by default.

    Your files in .agents/ override installed policies in .keystone/policies/.

  2. Deeper policies refine outer ones.

    Among policies, a policy nested deeper in keystone.json refines the policy it sits in.

  3. Strict locks absolutely.

    Nothing overrides a strict item. If a project file shadows one, keystone verify reports a violation.

Strict and required keys
Key4.x aliasLocks or requires items in
rulesguides.agents/rules/
hookssensors.agents/hooks/
skillsplaybooks.agents/skills/ (an item matches <item>/SKILL.md)
commandsactions.agents/commands/

strict items ship with the policy and lock. keystone verify reads them from each policy entry in keystone.json. required items don't ship with the policy. The policy's keystone-policy.json names them, and an outer layer must supply them. An outer layer is an ancestor policy or the project. A missing one is an advisory gap.

A 4.x key keeps locking the same items in the 5.0 folders, and inside a policy keystone also searches the 4.x folder. References aren't in the cascade, because they load on demand.

Hook depth limit

Only the project and top-level policies may ship hooks. If a nested policy ships a hook, or claims one in strict, keystone verify fails with a DepthViolation. The check covers both hooks/ and the 4.x sensors/ folder.

Provenance

Each index entry carries a provenance from its path: project, or policy/<name> for vendored content. Keystone pins each policy by version and content hash, and keystone verify resets drift. keystone charter show --effective prints the winning set and what each winner overrides.

ConceptsEvents →
Concepts

Events: host events and signals

event: names what fires a hook, a computational rule, or a tool. A host event comes from the host, so a failing hook can block there. A signal comes from keystone or from your own script, and no host sees it.

Host event

A closed set

PreToolUse, PostToolUse, UserPromptSubmit, Notification, Stop, SubagentStop, PreCompact, SessionStart, SessionEnd. Keystone bridges each one into the host's hook config.

Signal

Any other name

Keystone fires its built-ins from its own commands. Fire any signal with keystone signal fire <name>. Declare custom ones in keystone.json signals: for lint and discovery.

Built-in signals
pre-command  post-command   pre-playbook  post-playbook  pre-task  post-task
pre-verify   post-verify    on-gate       on-phase-enter  on-phase-exit
on-spec      on-plan        on-review     on-commit       on-learn
on-synthesize               on-audit      on-mode-change

For example, keystone verify fires pre-verify and post-verify, and keystone document promote fires on-gate.

What a fire does
  1. Select.

    It finds .agents/ from any subfolder and takes every primitive with this event: and a run:. There's no per-hook matcher, so a PreToolUse hook reads its stdin payload to pick the calls it checks.

  2. Run.

    It runs each command in parallel, with KEYSTONE_EVENT, KEYSTONE_PHASE, KEYSTONE_COMMAND, KEYSTONE_TYPE, and KEYSTONE_HOST set. On a host event, it also passes the host's event JSON on stdin.

  3. Dispatch.

    For inferential hooks, it prints a dispatch list: each subagent to spawn and the returns: schema to fill. The host's agent spawns them.

$ keystone signal list              # built-in and declared signals, plus host events
$ keystone signal fire pre-verify   # fire a signal by hand
$ keystone hook fire Stop           # run the hooks on an event; bridges call this

Both kinds of event reach the same dispatcher

Conceptsrule →
Constraints

rule

A directive the agent follows. Scope it with paths:; a rule without paths: applies everywhere. The cost: an inferential rule is only text, so the agent can ignore it. Pair it with a hook when a violation must block.

Example
---
id: idioms/go/stdlib-first
description: Prefer Go stdlib over new third-party deps.
paths:
  - "internal/**/*.go"
  - "go.mod"
corpus:
  - idioms/go/stdlib-first
---

# Stdlib first

## Iron law
- No new direct dep without naming the stdlib package it replaces.

## Rules
- Serialization uses `encoding/json` and `gopkg.in/yaml.v3`.

Save it as .agents/rules/idioms/go/stdlib-first.md. The topic folder only groups files. It doesn't change when a rule applies.

Frontmatter
KeyRequiredMeaning
pathsnoGlob list. Omit it to apply everywhere. It only narrows; it can't widen.
corpusnoReference ids that hold the reasoning. Lint warns when one doesn't resolve.
tiernoiron-law, golden-rule, or preference (the default). Only lint reads it.
modenocomputational makes the rule a check. Then event and run are required.
Body

Group directives under ## Iron law(s), ## Golden rule(s), ## Rules, and ## Anti-patterns. Host shims copy only those sections, so keep the reasoning in a reference. An iron law wins over any conflicting instruction. A golden rule yields to stated reasons, and a regular rule yields to a stronger one.

How each host gets it

Without paths:: one line in the AGENTS.md block, with its path and description. With paths:: a shim on Claude Code, Cursor, Copilot, Continue, and Cline. On other hosts, the agent finds it in INDEX.lite.json.

Computational: it fires through keystone hook fire like a hook, and a non-zero exit blocks. It gets no shim and no AGENTS.md line. Its paths: are documentation only.

Author it
$ keystone new rule <topic>/<name>   # also writes the paired reference
Constraintsreference →
Constraints

reference

The reasoning behind a rule: why it exists, what it guards against, and where it comes from. It costs no context until the agent opens it. The cost is reach: if no rule links it, the agent never finds it.

Example
---
id: idioms/go/stdlib-first
description: Why the Go code prefers the stdlib over new dependencies.
---

# Stdlib first, reasoning

Every direct dependency is code the team must audit and upgrade.

## Anti-patterns
- A dependency added for one helper function.

## Sources
- The Go standard library docs.

Save it as .agents/references/idioms/go/stdlib-first.md. Use the same <topic>/<name> as the rule it explains.

How the agent gets it

No host reads .agents/references/, so keystone projects nothing. The agent reaches a reference through a rule's corpus: field, or through MCP: keystone_get_reference id=<rule-id> returns the linked bodies. References also appear in INDEX.lite.json.

Keep directives out of a reference. The agent may never open it, so a directive there may never apply.

Author it
$ keystone new reference <topic>/<name>
Constraintshook →
Constraints

hook

A check that runs on an event and can block the agent. On a host that runs hooks, it's the strongest constraint keystone has. The cost is the binary: every machine that runs agents needs the 5.0 keystone on its PATH.

Computational

A command, an exit code

run: is a shell command. A non-zero exit blocks on a host event.

Inferential

A review, a verdict

The body is the review prompt. Keystone prints a dispatch list, and the host's agent spawns the review. It can't block on a host event.

Example
---
id: build
description: The project's build step.
mode: computational
event: Stop
run: go build ./...
---

# build

A non-zero exit means the build is broken. Fix it before you claim done.
Frontmatter
KeyRequiredMeaning
modein practicecomputational or inferential. Lint treats a missing mode as inferential.
eventto fireA host event or a signal. Without it, the hook never runs. See Events.
runcomputationalThe shell command.
returnsinferentialThe verdict schema the review must fill.
agentnoThe subagent to dispatch. The default is the hook's own id.
How each host gets it

Claude Code, Cursor, Copilot, Codex, and opencode get a bridge per host event. Every other host gets a report, and AGENTS.md tells the agent to run the checks in .agents/hooks/ itself. On Claude Code, an inferential hook is also written as a subagent. See Hooks and permissions.

If checks stop after an upgrade, a 4.x binary is still on PATH. Install 5.0 on that machine.

Author it
$ keystone new hook <id>   # event: Stop, run: "true"; replace the placeholder
Constraintspermission →
Constraints

permission

Which tool calls the agent may make freely, must ask about, or must never make. Write the rules once, in Claude Code syntax. The cost is uneven reach: where a host can't express a rule exactly, keystone reports it instead of enforcing it.

Example
---
id: default
description: Protect secrets and gate pushes.
allow:
  - "Bash(go test:*)"
ask:
  - "Bash(git push:*)"
deny:
  - "Read(./.env*)"
---

Tests run freely. A push leaves the machine, so it needs a person.

Save it as .agents/permissions/default.md. You can split rules over many files: keystone joins the allow, ask, and deny lists and drops duplicates. The body records why, and no host gets it.

How each host gets it
HostFileWhat translates
claude-codesettings.jsonEvery rule, unchanged, under permissions. Claude Code checks deny, then ask, then allow.
cursorcli.jsonallow and deny tokens. No ask. A Bash allow needs the cmd:* form.
codexkeystone.rulesBash rules only, as prefix_rules. ask becomes prompt, deny becomes forbidden.
the other sevenreportNo file. AGENTS.md counts the rules the host can't enforce.
Author it
$ keystone new permission <id>
Constraintseval →
Constraints

eval

A test that the charter behaves the way you expect. Run one when you add, scope, or prune a rule. The cost is reach: today an eval checks rule scoping and hook commands, and it can't yet check what an agent does.

Layout
.agents/evals/<id>/
├── EVAL.md          # frontmatter + the scenario in prose
├── expected.json    # the assertions
└── fixture/         # optional; the runner doesn't read it today
Levels
LevelStatusWhat it checks
staticrunsEach rule's paths: against touched_files, through rules_fired and rules_silent. The default level.
sensorrunsA hook's command: expect_exit and must_contain. It reads the first fenced code block in the hook's body, not run:.
agentskippedAn agent's behavior with the charter loaded. Not built yet.
Run it
$ keystone eval run                    # every eval; non-zero exit on any failure
$ keystone eval run --filter billing   # ids that contain "billing"
$ keystone eval run --baseline main    # compare against a git ref
$ keystone new eval <id>

With --baseline <ref>, keystone runs the ref in a git worktree beside your tree. Then it labels each eval as a regression, fix, new, removed, or stable. It exits non-zero only on a regression. An eval doesn't run by itself, so add keystone eval run to CI.

Capabilities

skill

A workflow the agent loads when the task matches its description. Each skill is a folder with a SKILL.md written to the Agent Skills spec, so most hosts read it as written. The cost is control: the host decides when a skill fires.

Example
---
name: release-notes
description: Draft release notes from the merged PRs since the last tag. Use when the user asks for release notes.
allowed-tools: Read Bash Grep
metadata:
  model: sonnet
---

# release-notes

1. Find the last tag with `git describe --tags --abbrev=0`.
2. List the merged PRs since that tag.

Save it as .agents/skills/release-notes/SKILL.md. Scripts and templates in the folder travel with the skill.

A unit of work the user asks for by name, such as /release. Where the host has slash commands, keystone writes one. The cost: a command does nothing until someone calls it. If the work should start from the task itself, write a skill.

subagent

A role the agent delegates to, such as a reviewer or a planner, with its own system prompt and tool list. The cost: its report is a claim, not evidence. Also, only Claude Code gets the tool list.

---

deviations, one per line, with the rule path.

Save it as .agents/agents/drift-reviewer.md. The folder is agents/, because every host with subagents uses that name. The body is the system prompt, and lint fails when tools is missing or empty.

Capabilities

tool

A callable you define: a shell run: handler with declared arguments. It isn't a host built-in like Bash or Read. The cost is trust: the handler runs with your full environment, and keystone doesn't sandbox it.

Example
---
id: open-pr-count
description: Count the open pull requests for a GitHub label.
transport: mcp
run: gh pr list --label "$KEYSTONE_ARG_LABEL" --state open --json number --jq length
args:
  - name: label
    type: string
    required: true
---

Save it as .agents/tools/open-pr-count.md. The MCP server serves it as keystone_tool_open_pr_count. To test it, run keystone tool run open-pr-count --label bug.

Transports
TransportStatusHow the agent reaches it
clidefaultAGENTS.md lists it with its keystone tool run <id> --<arg> <value> line.
mcpservedkeystone mcp serve serves it as keystone_tool_<id>, with :, /, and - turned into _.

How the handler runs
  1. Check.

    A missing required argument, or one the tool doesn't declare, fails the call before the handler runs.

  2. Export.

    Each argument becomes KEYSTONE_ARG_<NAME>, as a string.

  3. Run.

    Keystone runs run: with bash -c in the project root, and returns stdout and stderr together. A non-zero exit is a failed call.

With event:, a signal also fires the tool as a side effect, with the fire variables instead of arguments. The MCP server reads tools when it starts, so restart it after you add one. Don't name an argument dir: keystone tool run reserves --dir.

Author it
$ keystone new tool <id>   # transport: cli, run: ./scripts/<id>.sh
$ keystone tool list

document

A template for governed output, such as a plan, a review, or an ADR. Each filled copy moves forward through an ordered list of gates. The cost: keystone writes no copy for you, so the agent or a person fills it in.

Template and copy
.agents/documents/<id>.md        # the template; keystone index lists it
.keystone/work/<task>/<file>.md  # each filled copy; state, not indexed
Frontmatter
KeyOnMeaning
typebothThe subtype, such as plan or adr.
gatesbothThe ordered lifecycle. The copy needs its own list, because promote reads the copy.
gatecopyWhere the copy is now. If it's empty, promote treats the first gate as current.
produced_bytemplateThe command that writes copies.
Move a copy
$ keystone document list                                  # id, gate, and path of every copy
$ keystone document promote .keystone/work/PROJ-142/plan.md in-review

promote refuses a copy with no gates:, a gate outside the list, and any backward move. A forward move can skip gates. After it moves, keystone fires on-gate. A failing on-gate hook doesn't block, because the gate has already moved.

No host gets a document file. AGENTS.md describes the kind, and the agent opens a template when a command tells it to.

Author it
$ keystone new document <id>   # gates: draft, in-review, approved, executed, done

Context budget

How much charter text each host loads, in two tiers. Caps in keystone.json turn a regression into a failed keystone verify. The count is a word count, not a tokenizer count, so use it to compare files and set caps, not to predict cost.

Always loaded

Per host

Root files (AGENTS.md, plus CLAUDE.md on Claude Code). The id and description of each skill, command, and subagent the host lists. The full body of each pathless rule the host loads.

On demand

The same for every host

The full body of each rule, reference, skill, command, subagent, tool, and document, totaled per kind.

Caps
"budgets": {
  "always_loaded": { "max_tokens": 4000 },
  "reference":     { "max_tokens": 50000, "max_tokens_per_load": 3000 }
}
KeyFieldWhat it caps
always_loadedmax_tokensEach host's always-loaded tier.
a kind (rule, …)max_tokensThat kind's on-demand total.
a kind (rule, …)max_tokens_per_loadAny one file of that kind.
a 4.x keybothguides, corpus, sensors, actions, playbooks map to their 5.0 kind.

If two keys map to one kind, the stricter value wins. Set a field to 0, or leave it out, to leave it uncapped. Real tokenizers count about 1.35 times more than the estimate.

Where it runs

keystone budget prints both tiers and exits non-zero over a cap. keystone verify fails on the same caps. keystone init and keystone doctor print the tier per host but don't fail. MCP keystone_budget returns JSON, and the dashboard shows it at /charter/budget.

If the always-loaded tier is over its cap, run keystone allocate to find sections that can load on demand.

Allocate

keystone allocate converts an existing agent setup into .agents/. It reports each item's 5.0 kind and the path where it belongs, and it writes nothing until you pass --apply.

Host setups

What it reads

.claude/ (skills, agents, commands, rules, settings hooks and permissions), .cursor/rules, .cursorrules, Copilot files, .clinerules, .windsurfrules, .continue/, and .opencode/.

Root files

What it splits

CLAUDE.md, AGENTS.md, GEMINI.md, and .goosehints. It proposes moving each section that needn't load every session.

SectionBecomes
file patterns
A rule with paths:.
numbered steps
A command.
"before you commit, run X"
A hook.
long reasoning
A reference.
iron laws, security
Stay where they are, with keystone's managed block.
$ keystone allocate               # report only
$ keystone allocate --apply       # write new .agents/ files; change no original
$ keystone allocate --overwrite   # --apply, then hand the originals to keystone

With --overwrite, moved sections leave their root file and moved hooks leave settings.json. Each converted host file becomes keystone's, so the next keystone project replaces it. An original whose .agents/ target already existed stays as it is.

Governance

A change to the charter is an amendment. Amendments follow a fixed pipeline instead of ad-hoc edits, so you can read how the charter changed and who agreed.

The amendment flywheel
  1. Propose.

    The keystone-learn skill captures a surprise, an incident, or a review finding in .keystone/learning/inbox/.

  2. Synthesize.

    The keystone-synthesize skill promotes an accepted candidate to a rule or a reference, or rejects it with a reason.

  3. Ratify.

    A maintainer accepts the promotion in review. The change lands in .agents/ and gets indexed.

  4. Record.

    Record a material amendment as a document with type: amendment, or as an ADR when it's architectural.

Pruning runs the other way. The keystone-audit skill moves stale rules and references to .keystone/archive/, with a one-line reason. ADR 0010 records the 5.0 split into constraints and capabilities.

Roles and decisions

Maintainers merge changes, cut releases, and ratify amendments. Contributors open issues and PRs. Users' feedback is a first-class input to amendments.

Decisions run on lazy consensus. A merge needs a maintainer's approval and a green Code Health gate. A breaking change to the on-disk layout or frontmatter schema ships in a major release, with a migration and an ADR.

Upgrade from 4.x

keystone migrate up moves your files to the 5.0 layout. It never rewrites what you wrote, and keystone migrate down reverses it. Install the 5.0 binary first, because the host bridges call the installed keystone.

$ git add -A && git commit -m "pre-5.0"   # your restore point
$ go install github.com/tacoda/keystone/cmd/keystone@latest
$ keystone migrate up --dry-run           # print every step, write nothing
$ keystone migrate up
$ keystone index && keystone project
$ keystone verify

Adopt the 5.0 names

The 4.x names keep working, permanently: the old kinds, globs:, and on: all parse. I kept the migration to moves only, because a change to your frontmatter is one you should see and approve. keystone lint warns once per file, and keystone lint --fix applies the 5.0 spelling.

Move skill triggers: into the description by hand. 5.0 retires concern: keystone lint --fix inlines each concern into the primitives that include it. Then delete the concern.

If it stops

The migration stops before it moves anything when two files map to one place. The common case is .charter/guides/README.md beside a 4.x .charter/rules/README.md. Delete the rules/ one, then run keystone migrate up again.

If an old binary meets the new hooks, every tool call fails closed, including the install that would fix it. In Claude Code, type ! go install github.com/tacoda/keystone/cmd/keystone@latest yourself.
